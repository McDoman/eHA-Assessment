# Part 1, Question 2 — Facility Readiness, Accessibility and a Governed Spatial Database

Complete submission. Everything here is generated by the scripts in this folder.
**No source file was edited by hand** — in particular `LGA_SEN_Districts.xlsx`,
which is opened read-only and never written to.

## Run it

```bash
cd Outputs
python run_all.py
```

Full run takes about **65 seconds**. Stages can also be run individually, in
order. `run_all.py` stops at the first failure rather than carrying a broken
artefact downstream.

Requires: `geopandas`, `shapely`, `pyproj`, `pandas`, `numpy`, `scipy`,
`networkx`, `duckdb` (with the `spatial` extension, installed automatically on
first run), `openpyxl`, `matplotlib`.

## Pipeline

| Script | Task | What it does |
|---|---|---|
| `common.py` | — | Shared paths, CRS declarations, analytical parameters, logging, and the name-normalisation rule. Everything that matters is declared here once. |
| `01_crosswalk_normalisation_pipeline.py` | **1** | Reads the workbook read-only, expands merged cells, reconstructs the two-tier header, forward-fills the grouping columns, reconciles every administrative name, adjudicates duplicates and conflicts, validates against control totals, and writes the normalised table plus a full decision ledger. |
| `02_ingest_and_conform_pipeline.py` | — | Parses free-text coordinates (decimal, comma-decimal and DMS), repairs and quarantines them, reads the MapInfo `.mif`/`.mid` pair, re-assigns facilities to the ward that actually contains them, applies the published staffing norms, and reconciles the two population sources. |
| `03_spatial_database_pipeline.py` | **2** | Builds the spatial database: DDL with primary keys, foreign keys, CHECK and NOT NULL constraints, an explicit CRS registry, R-tree spatial indexes, governance views, and negative tests that prove the constraints actually fire. Also emits the PostGIS-equivalent DDL. |
| `04_access_analysis_pipeline.py` | **3** | Hybrid network / off-road travel-time model, population-weighted coverage from a demand-point grid, 2SFCA crowding index, and a full sensitivity sweep. |
| `05_gap_typology_and_outputs_pipeline.py` | **4** | Runs the fully-staffed counterfactual, separates staffing gaps from infrastructure gaps, ranks priority wards, draws the maps, and writes the results back into the database. |
| `run_all.py` | — | Runs 01 → 05 in order and verifies the expected outputs exist. |

## Three things worth knowing before reading the numbers

1. **PostGIS was not available in this environment.** The database is DuckDB +
   `spatial`, which enforces every constraint the task asks for. The identical
   schema is emitted as PostGIS DDL so nothing about the design depends on the
   substitution. Details and reasoning in `reports/03_database_validation.md` §1.

2. **The road network barely binds at 60 minutes.** At 5 km/h a 60-minute budget
   is a 5 km radius, and the supplied network is a 213-segment national skeleton,
   so the walk *to* the road consumes the budget before any road is reached — the
   network provides the fastest route for only 0.3% of covered demand points. This
   is measured and reported rather than glossed over, because it changes what the
   headline means. `reports/04_access_method_and_results.md` §6a.

3. **The level of coverage is far less robust than the ranking.** The headline
   moves from 14% to 86% across defensible off-road speeds. The *priority list*
   barely moves, because wards with nothing in range stay out of range at every
   threshold. Quote the ranking with confidence; never quote the percentage
   without its scenario attached.

## Known limits

Stated in full in `reports/05_findings_and_recommendations.md` §11. The largest
is that population is assumed uniform within each ward — no gridded population
was supplied, so within-ward distribution is unknown. The **classification**
(staffing vs infrastructure) is more robust than the **magnitude**, because it
depends on which facilities are in reach rather than on precisely how many people
are.
